## Key Learnings

- The original Terac webhook design looked up `ReviewStudy` indirectly through an existing `ReviewResponse` row (matched by `externalSubmissionId`), which meant an approval webhook arriving before the response POST (plausible with Terac's `auto_approve` review-task type) had literally nothing to update, returned `RESPONSE_NOT_FOUND`, and - critically - the webhook's own idempotency dedup (unique constraint on `provider + externalEventId`, checked purely by row existence, not by a "processed" flag) meant that single delivery was the only chance ever given to that event; there is no actual retry path that could recover it. This was a genuine, self-documented-but-unfixed limitation inherited from Phase 7's original implementation.
- The fix pattern that generalizes: whenever a webhook can race ahead of a client-initiated write for the same logical entity, resolve the target entity from data the webhook carries directly (here, `externalOpportunityId`, set on the study row at draft-creation time, well before any response could exist) rather than from a row created by the other side of the race.
- `pnpm db:generate` (i.e. `prisma generate`) requires a `DATABASE_URL` env var to load `prisma.config.ts` even when not actually connecting to a database - a dummy `postgresql://user:pass@localhost:5432/db` value is sufficient, same trick already used for `pnpm build`.
- AskUserQuestion's `options` array is capped at 4 items per question (not the 7 implied by the /compress skill's own instructions) - splitting into two 4-option (or fewer) questions in a single tool call works within the schema limit.
- `packages/domain/src/commands/parseCommand.ts` already recognizes `NEED`, `APPROVE`, `DECLINE`, and `DONE <code>` syntactically (with an explicit comment noting they're "handled by their own phases... -> Phase 8"), so Phase 8 work starts from wiring existing parse output rather than writing a parser from scratch.

## Solutions & Fixes

- **Bug:** Terac approval webhook arriving before the study response POST permanently and silently lost the approval (item stuck in `WAITING_FOR_REVIEW` forever, no error, no retry).
  **Fix:** `prisma/schema.prisma` - made `ReviewResponse.answers` nullable. `packages/db/src/teracApprovalFlow.ts` - rewrote `processTeracApproval` to resolve the study via `findStudyByExternalOpportunityId(event.externalOpportunityId)` first, returning `STUDY_NOT_FOUND` only if the opportunity itself is unknown (a real error case, not an ordering race); counting/`READY_TO_AGGREGATE` no longer depends on a `ReviewResponse` row existing. `packages/db/src/repositories/reviewResponseRepository.ts` - replaced `markResponseStatus` (update-or-P2025-fail) with `upsertResponseStatus` (creates a placeholder row with status set and null answers if none exists, or flips status on an existing row without touching its answers); `insertReviewResponse` now handles a P2002 conflict by `update`-ing the existing row's `answers`/`externalTaskId` (filling in a placeholder left by the webhook) instead of just returning the stale existing row unchanged. `apps/web/app/api/webhooks/terac/route.ts` - now passes `externalOpportunityId` through to `processTeracApproval`. Updated `packages/db/src/teracApprovalFlow.test.ts` and `packages/db/src/repositories/reviewResponseRepository.test.ts` to match the new contract, including a new test that specifically covers "counts an approval that arrives before the response POST."
